# Project data, chats and workbench

The interface now has one coherent hierarchy: the current project owns available data and durable chats. Selecting a chat binds its question, approvals and saved outputs; the adjacent workbench displays that chat's figures, code, evidence and display controls. The internal investigation identity and APIs remain intact but are not a separate product destination.

The project context button opens project details; Data opens actual bounded input discovery in a dismissible project panel. Project plans, runs, results and exports open one collection at a time in the same project browser, labeled with the project name and “Across chats in this project.” None replaces the selected chat or its output canvas. Known records identify and reopen their exact source chat; older records retain their analysis identity. Only the open collection is highlighted. Project counts use available input files and retained chats, including before an analysis job exists.

These project collections cover retained analysis-job records. Scientific methods, studies and scientific-only records remain available through the separate explicit Scientific records entry; a complete catalog across both workflow engines was not introduced. Explicitly reopening a chat rebinds its owned job even after a legacy-analysis view; background polling retains its cache.

Two draggable, keyboard-accessible separators resize navigation/chat/workbench. Navigation and workbench also collapse independently. A quiet toggle in the left rail header and another at the far-right edge reopen them and restore saved sizes. Both remain reachable at the screen edges when their panes are hidden. The central chat has an inset rounded surface and compact rounded composer. The chrome uses grey, black and white; scientific category colors retain their data meaning.

Local typography, outline SVGs and restrained press/hover/tab transitions improve readability and feedback without external assets. Supported browsers use an animated native customizable select picker; other browsers retain native controls. Keyboard behavior, existing select IDs and change handlers remain intact. Reduced motion disables animation; dragging is immediate. Pane visibility updates synchronously with CSS grid easing, independently of document view transitions.

The normal chat route always requests model planning and has no operator fallback or canned QC/batch welcome buttons. Historical operator authorship stays truthful in secondary evidence. The local model project is configured with the user's existing Codex model, `gpt-6.1-sol`, and the CLI authentication status was checked without exposing credentials. Its startup sharing scope is synthetic; each chat still requires its own sharing grant. Plan review and data-execution authorization remain separate. No live model reply was generated by these UI checks.

The main model-enabled project is served at `http://127.0.0.1:8878/`, with `8880` retained as an alias of the same service. Previously completed synthetic sample analyses are retained in their original project at `http://127.0.0.1:8879/`; frozen provider settings were not changed in place. Both use the same bounded synthetic input root and the final immutable source snapshot with guards enabled. These are real single-project services, not an invented multi-project backend.

The final source manifest, 171-check targeted JUnit, runtime identity, browser observations and screenshots are retained under `reports/workbench-refinement/2026-10-28/structured-chat-v8/`. Desktop project scope, source-chat opening, sample UMAP, rounded themes, dropdowns and pane controls were observed.
