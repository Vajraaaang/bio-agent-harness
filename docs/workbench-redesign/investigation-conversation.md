# Durable investigation conversation

`workbench-conversation.js` now adds a renderer for `devbench.investigation/1` records while preserving the existing legacy job renderer. It performs no HTTP calls and does not execute, approve or retry work.

## Host API

```javascript
const model = window.WorkbenchConversation.renderInvestigation(container, {
  investigation,
  config,
  jobState, // optional full authoritative job override; otherwise investigation.job_state
  onAction
});
```

The returned model includes `turns`, `profile`, `metrics`, `artifacts`, `synthesis` and:

```javascript
model.inlineGate = {
  kind: 'clarification' | 'review' | 'run' | null,
  investigationId,
  revision,
  jobId
};
```

For an empty investigation, `inlineGate` is `null` and the existing first-use view renders. `buildInvestigationModel` and `planSummary` are also exported for tests and host use. Existing `render`, `renderConversationWorkspace`, `buildModel` and `failureSummary` remain unchanged interfaces.

The host owns persistent `#review-form` and `#run-button` nodes in a stable sibling action host outside the renderer's replaceable container. Move those original nodes into the conversation rather than creating duplicate controls or values. The renderer provides the plan summary and gate text; it does not create approval checkboxes, reviewer fields or a competing run button. The host must preserve existing authoritative review/run handlers and permission checks.

## Explicit callbacks

| Callback | Trigger | Host responsibility |
| --- | --- | --- |
| `{type:'clarify', investigationId, expectedRevision, declarations}` | User submits the native clarification form after validity checks | Post the existing guarded clarification action using the current expected revision. Render the returned durable record. |
| `{type:'navigate', view:'results'}` | User chooses an artifact reference | Focus the synchronized artifact canvas. |
| Legacy `{type:'draft', question, sourceRunId, input}` | Existing legacy follow-up chip | Draft only; preserve source bindings and require a new explicit submission. |

Clarification dropdowns contain only backend-supplied option values; capture-unit options originate from actual observed columns. Missing values start with an empty `Choose an option` entry. The renderer never selects a scientific declaration on the user's behalf. Supplied declarations are preserved and updated only by explicit form values. Draft field edits survive a renderer update for the same investigation via per-container draft state. The frontend coordinator should also avoid replacing unchanged threads during polling to preserve focus.

## Evidence and history

The renderer prefers backend-derived `thread_turns` when available, otherwise uses `turns`. It preserves their order and IDs, accepting `kind` or `type` as the recorded turn discriminator. Five-step headings appear only for actual integer `turn.step` values in the source records. No future or completed stages are inferred from a desired workflow.

Data audits show four distinct sections: observed facts, supplied declarations, inferences and unknowns. Historical audits use their actual `turn.content`, so later declarations do not rewrite the earlier audit. Each historical plan uses its own `content.proposal` metrics and recorded status; a child investigation's current status does not relabel an ancestor decision. Earlier synthesis records remain accessible alongside the current synthesis.

The current review/run gate is derived only from the current investigation's linked `job_id` and actual job state. `awaiting_operator_review` yields the review gate, `approved` yields the run gate, and active execution has no approval/run gate. A retained `needs_information` reviewable proposal without a review receipt can also show the review gate. Startup execution permission still controls whether the host run button can act.

Four plan metrics are derived only from recorded values: input preview, workflow, integration setting and run/worker resource limits. Missing values display `Not recorded`. Figures, synthesis findings, method evidence assessment and uncertainties come from actual artifact/synthesis records; no biological results are generated by this renderer.

## Additional CSS classes

- `.wc-spine-heading` for recorded scientific-step headings.
- `.wc-data-audit`, `.wc-audit-grid`, `.wc-audit-section`, `.wc-audit-heading` for the four evidence scopes.
- `.wc-plan-review`, `.wc-plan-metrics`, `.wc-plan-metric` for the four-metric plan summary. Each metric is a `div` containing `dt` and `dd` inside the grid `dl`.
- `.wc-clarification`, `.wc-clarification-form`, `.wc-clarification-field`, `.wc-field-reason`, `.wc-clarify-submit` for native inline clarification.
- `.wc-inline-gate[data-inline-gate=review|run]` for host-controlled approval/execution context.
- `.wc-turn`, `.wc-turn-<recorded-kind>`, `data-turn-id`, `data-turn-kind` for recorded turns.
- `.wc-synthesis`, `.wc-synthesis-section`, `.wc-artifact-card`, `.wc-artifact-reference` for actual retained outputs and canvas links.

The earlier structured disclosure and motion contract remains active. Entry animations run only when investigation identity changes and respect reduced motion. All scientific text uses safe text nodes; raw JSON remains secondary.
