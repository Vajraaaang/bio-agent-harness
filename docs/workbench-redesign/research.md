# Workbench redesign: product and library research

Research date: 2026-10-28. This combines primary-source documentation with seven public browser captures inspected during this redesign, including a live public CELLxGENE Explorer. Authenticated reference workflows, accessibility compliance, timing performance, and private workspace behavior were not verified. Local implementation decisions must be checked against the actual workbench contracts.

## Grounding and design decision

The existing `devbench/analysis/assets/workbench-ui.html` is a standalone HTML application with inline CSS and one inline script; the inspected baseline contains no React or installed browser plotting runtime. It already has a conversation inspector, data/plan/run controls, results, and explicit scientific evidence text. Retain this deployment model and backend authority. A frontend framework migration would create substantial regression and packaging work without establishing scientific value.

Choose **Monochrome scientific precision**: white and neutral-grey surfaces, black primary text and actions, compact controls, 4 px spacing rhythm, thin boundaries, 6–8 px radii, and a prominent question composer. The user subsequently required a grey/black/white application UI; that instruction supersedes the initially considered teal accent. Scientific figure colors retain their recorded data scales rather than changing biological encodings to fit the UI palette. Keep the dataset, retained run, review state, and selected artifact visible. Use a primary conversation and an evidence canvas that expands only when needed, rather than making researchers navigate disconnected dashboards. Keep technical detail in accessible disclosure sections.

Three viable directions were considered:

| Direction | Character | Benefit | Tradeoff | Decision |
| --- | --- | --- | --- | --- |
| Monochrome scientific precision | White/grey/black, compact instrument-like controls | Strong readability and clear status hierarchy for long research sessions | Requires disciplined spacing and copy rather than decoration | Selected |
| Editorial laboratory (considered before monochrome instruction) | Warm paper, serif headings, terracotta accents | Welcoming reading experience for reports | Existing visual language is close to this; less effective differentiation between navigation, analysis, and evidence | Superseded for UI colors; retain warmth only in prose rhythm |
| Midnight instrument | Graphite surfaces, pale text, monochrome status labels | Useful for dense plots and low-light sessions | Harder to validate every plot/background combination; insufficient as the only theme | Optional dark theme, with explicit chart colors |

These are original design directions, not copies of the references' branding.

## Library evaluation

All license conclusions below concern the named open-source repositories, not similarly branded hosted services, paid templates, or optional enterprise products. Preserve the selected package's notice and transitive licenses when vendoring. No package is approved solely by popularity. Current release observations are a maintenance signal, not a guarantee of future support or security.

### Scientific rendering

| Candidate | Primary license and maintenance evidence | Compatibility, accessibility and performance | Decision |
| --- | --- | --- | --- |
| Plotly.js | [MIT license](https://raw.githubusercontent.com/plotly/plotly.js/master/LICENSE); [official free/offline explanation](https://plotly.com/javascript/is-plotly-free/); [release list](https://github.com/plotly/plotly.js/releases) showed 4.1.2 at review. | Standalone browser integration, scientific trace types, selection, zoom and export. | D3 | [ISC license](https://raw.githubusercontent.com/d3/d3/main/LICENSE); [release list](https://github.com/d3/d3/releases) showed 7.9.0. | [Official introduction](https://d3js.org/what-is-d3) describes low-level web-standard primitives. ## Selected implementation approach and acceptance criteria

Selected: the existing native DOM/CSS frontend, explicit design tokens, semantic controls, CSS transitions, and a dependency-free Canvas2D scatter renderer for bounded QC and retained UMAP observation payloads. Provide SVG/PNG/CSV/JSON exports and exact-ID selections through one reusable figure interface. Keep the existing server-side Matplotlib renderer for its supported scientific outputs. This avoids duplicating the renderer with a broad chart runtime and keeps assets compatible with the existing strict nonce CSP. Plotly remains the strongest evaluated future option for broader statistical plots. Plotly, ECharts, deck.gl, D3, Lucide, and React libraries are not selected for this implementation. Canvas2D is not WebGL/GPU acceleration, and this decision does not promise every RNA-seq chart class or unrestricted dataset sizes.

Keep any native renderer narrowly tied to genuine returned artifacts. Validate point counts, finite values, stable identities, known plot kinds, and display-control ranges. Visual settings must never submit a new scientific run. Unavailable coordinates, expression overlays, confidence estimates, or batch-adjusted results remain unavailable. Use a table/export fallback when a figure cannot render.

Benchmark on retained supported payloads and explicitly labeled synthetic stress workloads at 10k, 50k and, if relevant, 100k points. Measure initial parsing/render, resize, recolor, selection, and export separately. Record browser, hardware/viewport, workload construction, repetitions, full versus sampled counts, and retained limitations. Library performance statements are motivation only; they are not the workbench's benchmark results.

Verification must include keyboard navigation, focus recovery, responsive 1280/1440 widths, reduced motion, both selected themes, genuine error and empty states, approvals that stay blocked until the backend permits them, and saved-result retrieval. Screenshots demonstrate layout; they do not establish full accessibility compliance or scientific validity.
