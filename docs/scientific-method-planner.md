# Scientific-method planner

The planner separates scientific choice from execution availability. It uses the existing protected Codex selector and `MethodService`; custom methods and registered methods share the same run, artifact and proposal controls.

The governing explanation is: **data → question → appropriate methods and reasons → observed outcomes → conclusions and uncertainty**. A fixed-procedure smoke verifies execution and evidence handling; it does not determine the best method. Methods and parameters stay unspecified in a method-selection evaluation unless the user explicitly supplies a real constraint.

## Decision flow

1. Create a plan from an objective, coordinator-supplied observed/inferred metadata, explicit unknowns and immutable dataset artifact IDs.
2. Optionally retrieve primary-source text through an explicitly authorized HTTPS host allowlist. Retain its bytes and identity. Retrieval establishes what was fetched, not scientific authority or implementation correctness.
3. Generate scientific candidates in a fresh selector call without the registry. Preserve the candidate list and its order.
4. In a second call, resolve those frozen candidates against exact registered method versions. Unavailable candidates remain visible. New source evidence can be attached and resolution repeated before any trial is declared.
5. Have the trial-design selector propose comparisons, input states, subset-validity evidence, parameters, metrics, extraction paths and resource limits. Validate and declare the selected proposals before execution.
6. Run authorized trials on exploratory branches; derive metric values from actual run records, validation reports or frozen JSON artifacts.
7. Request a structured recommendation or explicit abstention. Review, full execution, canonical-plan change and experimental reuse have separate operations.

The scientific pass does not receive capability fields, registry records or implementation IDs. Structured capability fields embedded in supplied context are rejected recursively. The live selector uses a fresh actor workspace and protects the method workspace and previous actors. Command, MCP and browser activity remain prohibited inside these decision calls; authorized literature retrieval and execution are coordinator operations.

## Contracts and enforcement

`method_planner_contract.py` defines the phase schemas and prompts. The exported plan has six top-level fields: `task`, `dataset_summary`, `candidates`, `experiments`, `results` and `recommendation`.

New plans retain `evaluation_purpose` (`method_selection` by default, or `execution_verification`) and `user_parameter_requirements` outside that export. Each optional requirement is an explicit `{name, value, evidence}` record; evidence contains the source quote or reference. A new parameter claim with `origin: user` must exactly match a retained requirement. Assistant and fixture choices have their own origins. Task prose, an earlier suggestion, a default or a successful run cannot supply missing user-requirement evidence. Historical records remain readable without retrospective relabelling; their absent evidence stays unverified.

Hard preconditions use an observed metadata field, an operator (`equals`, `at_least`, `contains` or `present`) and an expected value. The controller recomputes their status. An inferred value cannot satisfy an unknown observed precondition. Violated requirements make the candidate inapplicable; blocking unknowns stop trial admission. Supplied metadata remain coordinator assertions, and should come from the existing dataset diagnostics rather than guesses by the selector.

New candidates and method contracts can declare `action_scope` with format `devbench.method-action/1`, intent `retain`, `diagnostic_flagging`, `exclude` or `infer`, interpretation `none`, `numerical_atypicality` or `qc_review`, and a Boolean `exclusions`. Retention and flagging bind exclusions to false. The coordinator's versioned `devbench.action-prerequisites/1` policy requires input integrity, unique observation identities and finite measurements for each intent. QC interpretation additionally requires known assay semantics; exclusion needs supported evidence and explicit authorization; inference needs known semantics, independent biological units and an identifiable design. Inference that permits exclusions inherits the exclusion requirements. Model assumptions may add requirements, never waive these minima. Legacy records retain their conservative prerequisites and original identities, without guessed scope or backfill.

Scoped observation candidates receive a bounded coordinator inspection of immutable inputs before admission and each execution or approval-dependent action. Finite types/identities are checked within the observation format's 10,000-row, 128-measurement and 16 MB limits; requested measurement variance/rank computations additionally cap the matrix at 100,000 values. The coordinator retains `method_prerequisite_inspection` records and audit references, including failures. The supplied context remains unchanged. Unsupported representations or failed inspections remain blocking, rather than acquiring fabricated observations. Measurement rank is a numerical property of that representation; it does not establish design identifiability, biological independence or causation.

The additive `observation_diagnostic` comparator requires coordinator-declared `validation.diagnostic_policy` (`devbench.diagnostic-policy/1`, interpretation and measurement semantics) and a matching diagnostic action. It accepts only an exact-input-bound `devbench.observation-diagnostics/1` object: `input_sha256`, `evidence_scope`, full ordered `retained_ids`, and ordered `records` with `observation_id`, status `flagged`/`not_flagged`/`unavailable`, finite score or null, reason and bounded evidence references to the observation's declared immutable measurements. Every input identity must appear exactly once in input order. Unavailable scores are null with an explanation. Unknown assay semantics permit generic numerical atypicality, with no technical-damage label; declared semantics permit “warrants QC review,” never proof of damage or causality. Exclusion requires a distinct approved action. A plain `retained_ids` output remains the unchanged retention interface and cannot masquerade as flag evidence.

`extract_observation_diagnostics(before_path, after_path, policy)` validates first and returns actual flag/unavailable IDs, hashes and `independent_diagnostics` containing input-derived `measurements`, `group_flag_rates` and `stability`. With no matched perturbation outputs, stability is null with a reason; neighboring-row agreement is not a substitute. These public descriptive measurements and candidate predictions do not establish detection accuracy or meet the comparative-winner floor. A null recommendation can still report a useful diagnostic next step. Non-exclusion actions cannot silently remove or reorder observations; scoped retention/exclusion contracts require an observation-effect comparator rather than structural JSON/file validation.

The coordinator's receipt-verified evidence assessment returns `diagnostic_next_steps` separately from comparative selection. Each step binds the candidate/run, interpretation, flagged/unavailable counts and a descriptive review or missing-evidence request, with `exclusions_authorized: false`. This additive response is derived from actual successful diagnostic receipts; it does not add fields to legacy recommendation artifacts, backfill historical plans or relax the winner floor.

Diagnostic reasons use coordinator-admitted exact language from `devharness_core.methods.diagnostic_reasons(interpretation, status)`: numerical flags say `Unusual under the supplied representation`, numerical nonflags `Within reference`; QC flags say `Warrants QC review`, QC nonflags `No QC review flag under the supplied reference`. Unavailable reasons are `Reference unavailable`, `Measurement unavailable`, `Score unavailable` or `Insufficient evidence`. Free-form affirmative damage/causal statements and suffixes are rejected deterministically rather than through keyword matching. Any raw candidate explanation stays in separately retained untrusted drafts/refused outputs; it cannot widen admitted scientific scope.

Prerequisite inspection receives the actual bound method's declared `sample_key`, `qc_metrics`, `counts_layer` and dataset artifact type. Before binding, an explicit coordinator `dataset_summary.observed.observation_input_policy` can supply these roles; the inspector never guesses metadata roles from column names. Custom sample columns therefore remain metadata. Scoped `single_cell_qc` AnnData contracts use the existing bounded HDF5 reader and their declared count representation, identities, sample column and QC metrics, rather than the JSON reader. AnnData inspection inherits the existing 100 MB file, five-million-value and 64 MiB decoded-data limits; rank/variance still cap selected numerical computation at 100,000 values. No transformed representation or new scientific inference is introduced by this compatibility check.

Public `diagnostic_measurements` has scalar `flag_rate` and `available_fraction` plus a distinct `by_measurement` map. Valid measurements named `flag_rate`, `available_fraction` or `by_measurement` remain supported inside that map and cannot overwrite aggregate fields. Declared `sample_key` supplies sample flag-rate grouping. Scoped retention and diagnostic methods require exactly the validated `dataset` output port, preventing auxiliary filtered or transformed datasets from escaping validation; the coordinator creates plots separately. Scoped AnnData retention additionally preserves `.X`, all matrix slots/layers, raw representation and observation/variable annotations, even when `counts_layer` points elsewhere. Identical H5AD reserialization remains valid. Legacy unscoped contracts retain their original output/comparator semantics. This does not introduce general validation of arbitrary inference/statistical output ports.

Scoped retention also preserves complete `.uns` metadata, including nested numerical measurements. Semantic comparison is bounded to 32 nested levels and 10,000 mapping/sequence nodes within the existing HDF5 read bounds; exceeding a bound produces an explicit validation failure. Because full ordered axes are already verified, retention compares complete matrix-slot values directly. DataFrame/Series slots use labeled `.equals` comparison, including `varm` and `raw.varm`, rather than integer indexing that could mistakenly select columns. Legacy subset slicing remains unchanged.

Full-dataset trials must use the declared original artifact IDs. Smaller trials require an immutable inspection JSON artifact containing `input_artifact_ids`, `parent_artifact_ids` and `dataset_summary`; its observed metadata must preserve the candidate's hard preconditions. This supports representative complete libraries, replicate-preserving pilots and other scientifically justified subsets. A rationale saying “use 10% of cells” alone does not admit a trial.

Trial declarations are immutable, and the comparison criteria cannot be redesigned after results have been observed. Declare all comparisons before running them; an adaptive follow-up needs a new planning cycle. Candidate comparisons require the same input artifact set. The controller validates method parameters and refuses resource declarations below the selected methods' limits. Each trial executes once. Method process limits are enforced by the underlying runner. The trial elapsed-time budget also stops further candidates and records over-budget outcomes.

For an explicitly justified missing or adapted implementation, `draft-method` asks a separate selector for source text, an algorithm summary, introduced choices and references. The operator supplies an immutable method interface, pinned image, lock and resource policy. The model cannot change that interface or choose host execution. The controller checks references against supplied retrieval evidence, syntax-checks Python without executing it, hashes the actual source, and registers a custom/unreviewed version. Generated source remains unexecuted until an independently authorized trial. Implementation changes are frozen once a trial is declared.

Metrics have a predeclared category, direction, interpretation and source. Sources can select measured runtime/output size, validation fields, or finite numeric/boolean values in immutable JSON outputs. The controller rechecks declarations, execution evidence, artifact bindings and extracted values before recommending or approving. Missing values produce partial evidence; failures retain their errors. Explicit final-hypothesis p/q-value names, significant-gene counts and aliases in their JSON-pointer paths are rejected as selection metrics. Calibration diagnostics such as `null_fdr` remain available.

Recommendations cannot invent successful trials, change tested parameters or assert approval. A selected candidate needs eligible preconditions and actual successful trial evidence. Custom/generated implementations retain low implementation confidence. High scientific confidence is refused while plausible candidates remain untested. `choice: null` with `no_recommendation` remains a valid outcome.

Execution-verification plans cannot select a scientific winner. Method-selection choices also need the controller's comparison-evidence floor: a frozen joint comparison covering eligible implemented alternatives on matching immutable inputs, successful comparable results, and shared directed finite numeric scientific metrics computed by coordinator validation. Runtime/memory diagnostics, raw retention mechanics, structural pass flags and values reported by the candidate itself do not meet this floor. The controller-owned `recommendation_evidence_assessment` records its reasons and limitations separately from the model's answer. Unsupported choices fail and retain their raw response; the controller does not rewrite them into a successful abstention. Unavailable alternatives remain explicit limitations.

The single-cell comparator retains output `qc_quantiles` as candidate-supplied diagnostics. Its separate `reference_qc_quantiles` use immutable input annotations selected by verified retained observation IDs. Exact metric paths carry coordinator provenance only when observation identity, variables, retained counts and declared sample assignments are preserved. These reference annotations are not recomputed from raw counts, and the comparator does not establish their scientific validity. Comparison admission checks this provenance in sealed run validation and requires the same measurement basis across candidates. Each new approval-dependent recipe, proposal or full-execution action rechecks the current evidence floor, including for historical approvals; existing records remain unchanged.

This floor is a necessary software guard, not an independent scientific evaluation or a guarantee that the chosen method is optimal. The appropriateness of diagnostics, error tradeoffs, tuning/evaluation separation and external evidence must still be established for the particular dataset and objective. A method-unspecified evaluation must test those decisions rather than merely verify that one chosen procedure executes.

## Diagnostic profile admission

Before scientific candidate selection, the coordinator uses the existing bounded observation inspector for the three universal input facts when one immutable JSON or AnnData artifact has explicit observation roles. JSON requires declared `qc_metrics`; AnnData requires a declared count representation. Unsupported artifacts or missing roles produce retained unavailable inspection evidence without an observation data read. Only `input_integrity_valid`, `observation_ids_unique` and `metrics_finite` are requested at this stage. The selector receives a detached observed summary, `observation_fact_catalog` and `prerequisite_inspection` with the retained inspection identity, origin, artifact identities, declared hash, actual inspected hash when available, and failures. For recognized observation inputs, failed inspection withholds caller assertions of successful universal checks and retains a blocking diagnostic unknown. Missing roles or unsupported artifacts receive receipt-only unavailability, without adding observation blockers to unrelated general plans. The stored caller summary and prior state remain unchanged; no method registry is read. Binding and execution still reinspect the exact input with the method's declared policy.

`metrics_finite` is the exact machine field for numeric typed finite measurements. These checks establish bounded parse, identity and type integrity, not biological validity, independence, assay semantics, design identifiability, covariance suitability or nonzero profile scale. Necessary unobserved hard requirements remain blocking; the coordinator neither invents aliases nor removes them.

Scientific profile schemas remain open to unavailable families and aggregations. Their descriptions and the scientific prompt explain canonical mathematical serialization before availability: `absolute_mad` uses absolute deviation from the reference median divided by the unscaled median absolute deviation, without a 1.4826 factor, and leaves a zero-scale score unavailable. `empirical_two_tail` uses `1 - 2 * min(Fmid, 1 - Fmid)`, where `Fmid = (number < x + number <= x) / (2 * n)` within the frozen reference, including the observation and half weighting ties. `max` takes the maximum declared measurement score and yields a null aggregate if any score is unavailable. Empty `group_by` means a pooled input reference. These are mathematical identifiers, not a method recommendation or package-equivalence claim. The selected family, ordered measurements, reference groups, aggregation and threshold must bind exactly; prose is never normalized into an executable family. Unsupported alternatives remain scientific candidates with unavailable execution, and methods or thresholds become user requirements only through explicit retained matching records.

## Explicit approval scopes

- `review` approves the exact recommendation, with a recorded actor and rationale.
- `prepare-full` creates a concrete step over the original input artifacts. `review-full` approves that step. `run-full` additionally requires explicit data-execution authorization.
- `propose` creates a pending `MethodService` proposal. A subset pilot cannot be proposed as the full analysis. After an approved full run, the proposal uses its verified output. The existing `methods approve` operation commits the canonical revision and retains its stale-revision checks.
- `save-recipe` creates a frozen experimental recipe containing the method version and parameters. It does not change historical implementation trust or promote the method.
- Trusted-registry promotion remains a separate, unimplemented validation/governance workflow.

Per-plan leases serialize mutations. Orphan selections and runs can be recovered as interrupted attempts, with failed result rows and no invented metrics or automatic retry. Plan-state snapshots and method execution DAGs retain decision and execution history. Local actor labels are caller assertions; deployment authentication and independently retained audit roots remain operational responsibilities.

## CLI and Python

Use `devbench-analyze methods planner --help`. The matching Python API is `ScientificMethodPlanner(MethodService(absolute_workspace))`.

```sh
devbench-analyze methods planner --workspace /analysis/method-workspace --actor researcher \
  create --request /analysis/planning/request.json

devbench-analyze methods planner --workspace /analysis/method-workspace --actor researcher \
  --decisions /analysis/planning/scientific-decision.json science --plan PLAN_ID

devbench-analyze methods planner --workspace /analysis/method-workspace --actor researcher \
  --decisions /analysis/planning/resolution-decision.json resolve --plan PLAN_ID \
  --versions /analysis/planning/method-version-ids.json
```

The request contains `task`, `dataset_summary`, optional `prior_state`, `data_classification`, `evaluation_purpose` and `user_parameter_requirements`. The Python `create` method accepts the same optional metadata. Use `show --plan` for the six-field plan, `state --plan` for coordinator history, and `recover --plan` for explicit interruption reconciliation. `design-trials --plan` returns unexecuted proposed specifications. Trial commands are `declare-trial --plan --branch --spec` and `run-trial --plan --experiment --allow-data-execution`. `draft-method --plan --candidate --interface --environment-lock --justification` creates an experimental implementation from a separate structured selector response; the interface and lock arguments name absolute files.

Recorded decision files are offline fixtures or explicit decision replays. They are labelled `recorded_fixture` and never counted as live model evidence. Live calls instead require an explicit `--model`, disjoint absolute `--actor-workspaces` directory and `--allow-model-execution`. Only plans classified `public` or `synthetic` can enter a live selector; private, clinical and unclassified contexts are refused. The adapter retains its permission probes, provider identity checks, event capture, deadline and memory controls.

Codex documents `--output-schema` for structured responses in its [non-interactive interface](https://learn.chatgpt.com/docs/non-interactive-mode#create-structured-outputs-with-a-schema). The implementation-draft schema uses that flag and mandatory local validation. The other planner schemas include optional fields and open metadata maps, so the existing compatibility path stages a protected exact schema and validates locally. Every method-planner prompt includes its literal schema so it is available without a forbidden file-read tool call. Offline protocol tests do not establish live selection or code-generation quality.

## Verification and scope

`scripts/verify_method_planner.py` is explicitly an `execution_verification` fixture with recorded decisions. Its MAD parameters are fixture-author choices. It preserves an unavailable candidate, verifies the predefined ten-row software fixture becomes eight rows and confirms sandbox probes. It records abstention and checks that scientific recommendation approval, a scientifically selected recipe and a selected-winner proposal remain blocked. Canonical analysis and implementation trust stay unchanged.

Evidence is in `reports/extensible-methods/2026-09-27/`. The record distinguishes unit/protocol fixtures, real synthetic container execution, numerical verification and optional dependency failures. No live Codex method-selection performance, real biological cohort analysis or clinical validation is claimed.

The later [operator-assisted live smoke](../reports/rna-agent-readiness/2026-09-30-live-codex-smoke.dwb61822/README.md) verified execution, preservation, browser review and restart. Its original attribution of MAD/4 as user-prespecified was incorrect and is explicitly corrected while retaining historical prompts and receipts. It did not compare methods or establish scientific superiority; the live recommendation abstained.

The current implementation provides the backend and CLI, including source drafting as inert text through a tool-less model actor. Package installation, environment builds, a browser conversation UI and registry promotion qualification remain separate integrations. An outer workflow can also author source and register it directly through the same custom-method API. Large/chunked artifacts, remote HPC executors and institutional governance remain subsequent work.

## Version 2 numerical profiles and deferred decisions

New scientific candidates may freeze `diagnostic_profile` before registry exposure: `family`, ordered `measurements`, reference `group_by`, `aggregate`, and `flag_threshold`. Scientific family and aggregation descriptions remain open to unavailable implementations. Capability binding must match the entire frozen profile exactly; it cannot add a profile, change reference groups, or choose a cutoff after outcomes. Choices remain assistant/fixture choices unless explicitly supported by matching user parameter requirements. Historical candidates without this field and version 1 contracts remain unchanged.

`devbench.diagnostic-policy/2` currently verifies `absolute_mad` (absolute deviation divided by unscaled reference MAD) and `empirical_two_tail` (one minus twice the smaller empirical midrank tail). The latter uses `u=(strictly smaller + half the tied count)/reference size`; larger scores represent numerical atypicality, not technical damage. The reference includes each observation and either the pooled data or exactly the declared metadata grouping. Other families remain unavailable to this arithmetic verifier rather than acquiring a fabricated fidelity check. `max` aggregates all declared measurement profiles, and is null if any is undefined. Constant MAD references have an actual zero-scale reason; tied empirical ranks remain computable. Extreme finite ranges do not justify fabricated zero scales or scores. A strictly positive exact MAD ratio that underflows to floating zero is null with `Score below floating representation`; an actual median deviation of zero remains available zero. Calculations are bounded to 100,000 measurement values.

`devbench.observation-diagnostics/2` preserves the same ordered full-input envelope as version 1. Each record contains `observation_id`, `score`, `score_reason`, `flag`, `flag_reason`, `profiles` and `evidence_refs`. Per-measurement profiles contain `score`, `reason`, `reference_count` and `reference_group`. Available scores use null reasons; genuine arithmetic absence uses null with `Zero MAD in reference`, `Nonfinite score calculation` or `Score below floating representation`. Undefined aggregate uses `Profile score unavailable`. Missing assay semantics or categorical cutoffs cannot erase computable profiles. Every measurement has a bounded reference resolving to that exact immutable observation's input measurement.

Categorical decisions are separate: a null frozen threshold produces null `flag` with `Flag threshold unresolved`; undefined aggregate under a known threshold produces null with `Profile score unavailable`. Otherwise `flag` is exactly `score >= flag_threshold`, with the existing scope-bound canonical flagged/not-flagged reason. A deferred decision does not classify an observation as normal and does not indicate that its numerical profile is absent. All observations remain retained; exclusion still needs a distinct authorized action.

The coordinator independently recomputes and verifies values, reference populations, reasons, coverage and decisions. A candidate assertion of fidelity is insufficient. Version 2 receipts/extraction expose `score_available_ids`, `deferred_flag_ids`, `diagnostic_profiles`, `profile_metrics` and `arithmetic_fidelity`. The latter proves only the declared arithmetic. `available_fraction` measures aggregate numerical coverage; `decision_fraction` measures categorical coverage. `flag_rate` and group flag rates use decided observations as their denominators and are null when none are decided. Per-measurement coverage remains visible when one undefined profile prevents a complete aggregate. Score means/maxima are independent descriptive summaries, with explicit reasons for null values.

Receipt-bound `diagnostic_next_steps` include available-score and deferred-flag counts, profile summaries and arithmetic fidelity separately from the comparative winner assessment. Correct formulas, structural preservation, runtime and continuous-score coverage do not establish a superior method, biologically valid quality labels, independent replication or expert-level performance. Stability remains null unless appropriate matched perturbation outputs are supplied. The existing winner evidence floor and version 1 replay semantics remain unchanged.
# Independent evidence attachment

`attach_model_campaign` binds an admitted shared model budget before the first
parent call. `attach_investigation_evidence(session_id, bundle_ref,
expected_plan_hash=..., actor=...)` validates actual immutable child captures and
current dataset, requirement, source, runtime and schema bindings, then adds
stage-scoped evidence links only. It cannot select a method, change a fit, approve
a recommendation, or grant execution authority. Charged pre-fit reassessment
precedes capability resolution; a charged post-fit preliminary explanation may
nominate a later fork. Existing protected parent calls receive a bounded verified
projection and preserve failures and disagreement. See [independent
investigations](rna-independent-investigations.md) for the explicit caller mode,
campaign controls, and offline qualification limits.
