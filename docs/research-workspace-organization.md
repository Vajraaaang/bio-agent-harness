# Research workspace organization

Adopted direction, 2026-09-27: **Workspace → Project → scientific objects → typed provenance relationships**. This incorporates the supplied [Research Workspace Organization for Scientific Analysis](../reports/rna-agent-readiness/2026-09-27-organization.gs5lm60x/research-organization.txt) and the subsequent [Audit of the Research Workspace Organization](../reports/rna-agent-readiness/2026-09-27-organization-audit.iro5gaqt/research-organization-audit.txt). The retained audit SHA-256 is `bc080d56615feaf6d791af92c6752bbfc8d6810e997a15f90821d7b38c212187`.

The September 27 increment organized the existing single-user local service and strengthened its metadata persistence. The subsequent [shared scientific workspace implementation](shared-scientific-workspace.md) adds a bounded single-project record layer and browser workflow over the existing method store and controllers. It does not start M2b, add computational methods or provider permissions, or change scientific methods, resource ceilings or presentation-only semantics. Audit recommendations are requirements; they are not execution authorization. The audit expressly did not inspect private source or tests, and both supplied documents contain unresolved internal citation markers. Their vendor comparisons have not been independently verified here.

## Workspace and state terminology

| Concept | Meaning and boundary |
|---|---|
| Workspace | Future administrative/research namespace containing projects, membership and policy. The hierarchy does not establish a working multi-project authorization system. |
| Local service workspace | Existing protected on-disk service root with one durable local project, controller records and runtime ownership. Its filesystem location is not a scientific object identity. |
| WorkspaceViewState | Restorable UI state: route, exact selected objects/versions, inspector, zoom, filters and draft. It is not scientific evidence or an execution grant. `workspace.json` may retain its existing filename while storing project metadata and this view state. |
| Durable scientific records | Input and artifact identities, approved bindings, controller records, receipts and immutable bundles; future versioned objects reference these records. |
| Ephemeral runtime state | Kernels, in-memory objects, sockets, process handles, secrets and transient locks. Restoring references does not restore these resources or prove worker liveness. |

## Local increment

| Requirement | Implementation boundary |
|---|---|
| Durable project context | One stable local project ID and editable name per protected service workspace. This is not a multi-project or multi-user permission system. |
| Stable navigation | Overview, Inputs (verified content), Analyses & plans, Runs, Results, Files & exports; New analysis is separate. Recent work is bounded to three entries with honest Analysis request or Presentation badges. These labels describe existing records, not new Analysis/Result/Conversation registries. |
| Content identity separate from location | Group inspected inputs by recorded SHA-256 while preserving distinct registrations and locations. Identical verified bytes at different paths may share content identity; changed bytes at the same path remain distinct. Uninspected registrations stay unverified. A content hash is not a logical Dataset ID. |
| Analysis request separate from execution | Saved questions/plans are separate from numbered controller attempts. Presentation renders retain their operation kind and parent. Queued input inspection is activity, not an invented numerical run. The future Run/ExecutionAttempt hierarchy is not created by relabeling these views. |
| Activity and search | Local active/attention counts and searchable retained metadata/identities. Search does not open matrix contents, perform semantic retrieval or invoke a model. The controller remains authoritative for finalization, cancellation, recovery and unknown liveness. No implied cross-project/HPC activity or worker reconnection. |
| Results with context | Exact source analysis, input, proposal, operator review, bundle, figure payload and presentation identities are available in Provenance. No automatic canonical designation or independent scientific-validation claim. |
| Contextual inspector | Discussion labels the existing question/decision record. Execution Log identifies source analysis and selected presentation attempt. Code, Environment, Review and Display stay contextual to the selected record/version. |
| Files & exports | Existing verified artifact and bundle downloads. No file moves or unrestricted filesystem browser. File names and folders do not define the scientific hierarchy. |
| View restoration | Save view, selected analysis/figure/version/root, tab/visibility, zoom, search/filter and unsubmitted question. Disclose missing/changed saved artifacts rather than silently substituting. Input declaration forms, unsaved styling and kernels are not restored. |
| Durable local metadata | `workspace.json` stays outside immutable scientific records. Schema validation and a strict field allowlist exclude tokens, credentials, execution settings/grants and transient process state. Expected revisions reject stale saves; authentication is still required after reload/restart. |

The persistence baseline already has version-one format validation, expected-revision checks and a synced temporary file followed by atomic replacement. The audit correction uses `devbench.workspace/2` with `schema_version: 2`; the API revision retains stale-save protection and `ui` remains the WorkspaceViewState projection for compatibility. Valid version-one metadata migrates with project ID, revision and view state preserved and the previous snapshot retained. The additions include `workspace.previous.json`, directory synchronization and explicit startup recovery: missing/invalid existing metadata fails closed by default; recovery validates the selected backup and quarantines an invalid primary without downgrading unknown schemas or restoring scientific jobs/grants. See the [operator documentation](workbench-ui.md) for recovery commands. **The additions have focused tests and actual browser migration/recovery evidence in the [audit checkpoint](../reports/rna-agent-readiness/2026-09-27-organization-audit.iro5gaqt/README.md). The shared-workspace broad run and frozen-source retests are reported separately; the broad suite is not green.** Recovery must disclose its source/revision rather than silently substitute an older saved selection.

## Required future object contracts

These define the object contracts. The opt-in local scientific layer now implements Study, Dataset/Analysis versions, explicit invocations/attempt links, Result versions over existing immutable artifact identities, ValidationRecords, append-only reviews and scoped result selections. The broader administrative Project, PlanVersion, durable discussion, multi-project permissions and later contracts remain backlog requirements. Names, paths, navigation labels and collection membership do not establish identity.

| Object | Contract |
|---|---|
| Project | Durable administrative, persistence and collaboration boundary with explicit members, permissions and policy. Cross-project references require the current intersection of access rights. |
| Study | Durable container for a unit of scientific work, with stable ID, title, aim/question, status and dataset/analysis/result references. Protocols and hypotheses may begin as typed linked documents/metadata; they are not interchangeable meanings of Study. |
| Dataset / DatasetVersion | Dataset is logical identity. Each immutable DatasetVersion records a versioned manifest/snapshot of member content hashes and relevant metadata, with separate physical locators. Renaming a Dataset or moving a locator preserves its identity and unchanged content version; changed member bytes or scientific manifest metadata creates a DatasetVersion. Biological units are scientific metadata, never inferred from folders. |
| Analysis / AnalysisVersion | Stable analysis identity with immutable versions of workflow/method, code and scientific parameters. A scientific code/parameter change creates an AnalysisVersion; repeating an unchanged invocation does not. |
| Run | Intentional invocation of an exact AnalysisVersion with exact input versions, parameters, environment and trigger. A separately requested rerun creates a new Run. Store attributable timing, outcomes and links to controller evidence; terminal records remain immutable. |
| ExecutionAttempt / Job | Controller realization of a Run on a worker/process/scheduler. A retry of the same invocation creates an attempt under the same Run, preserving failed/cancelled attempts and receipts. It is not a second scientific invocation. Reconcile actual ownership and liveness; unknown remains unknown. |
| Result / ResultVersion | Scientific meaning, interpretation, originating Run references and review state. Each version can be candidate, reviewed or rejected and can be selected for a scoped canonical role. Result versions retain the evidence supporting their interpretation; latest never implies canonical. |
| Artifact / ArtifactVersion | Materialized bytes with media type, content hash, locator, version and generating Run/attempt/receipt references. An artifact version may materialize or support several ResultVersions, and a ResultVersion may use several artifact versions. Representation/version identity is separate from scientific status. |
| Plan / PlanVersion | Draft → in review → approved/locked → superseded. Method changes require versioned reviewed amendments. Cosmetic figure edits retain the scientific plan and AnalysisVersion; they produce a presentation/artifact version with unchanged scientific data. |
| Method / Recipe / MethodVersion | Reusable method identity and immutable implementation versions, distinct from a particular Analysis. Record built-in/imported/user-authored/LLM-generated origin, code/tool/package/container identity, I/O contracts, parameters/defaults, assumptions, evidence and required permissions/resources. Trust and approval are explicitly scoped; generated/custom versions begin experimental, not supported scientific policy. |
| ValidationRecord | Binds an exact MethodVersion to tests/fixtures/invariants, environment, input identities, validation outputs, executor, reviewer, status and time. Execution success alone is not validation; local approval, broader supported status and clinical qualification remain distinct. |
| Conversation / ConversationBranch | Append-oriented project record with messages/tool results, ancestry, purpose and immutable context references. Reopening restores this history and its exact anchors, not a kernel or prior access grant. |
| Annotation | Author/text anchored to an exact ArtifactVersion and optional region/selection with stable selection IDs and population/layer semantics. |
| Collection / tag / field | Optional logical references, not file moves. Multiple memberships and saved filtered views preserve identity and provenance. |

Canonical selection is an attributable pointer to an exact ResultVersion within an explicit scope such as `(study_id, result_role)`. Promotion records the actor, time, review/basis and superseded pointer. Replacing the selection supersedes the prior result **for that scope** without deleting it or changing its role elsewhere. A global Boolean on an artifact cannot represent this contract.

Add narrowly scoped metadata around existing controller records and receipt roots. Do not duplicate execution engines, scientific tools, bundles or the controller state machine, infer historical Run/attempt groupings without evidence, or rewrite sealed records to fit the new vocabulary.

## Anchored discussion, branches and proposals

A substantive side conversation is a branch with an explicit purpose. Its immutable context snapshot references project, Study, DatasetVersion(s), AnalysisVersion, Run, ArtifactVersion, selection/population/layer, environment, PlanVersion and parent discussion revision. Preserve the exact base versions. If a parent changes, the branch stays anchored to its base and is visibly stale relative to the new version; it does not silently retarget. A mutation proposal must check the target's current revision and require explicit conflict resolution/rebasing when its base is stale, retaining the earlier proposal/history.

Branches inherit references. Effective permissions are reevaluated when references are opened, content is read, proposals are accepted and execution is requested, using the current access intersection. A historical permission snapshot is audit context, never a durable grant. Revocation must deny current content access even when earlier access is recorded; retain only lineage metadata the current actor may see. Branches do not inherit secrets, credentials, standing remote-compute approval, unrelated job control, mutable kernels, open handles or uncommitted changes. Exploratory changes cannot silently mutate parents, canonical results, approved plans or original files.

Return typed proposals: note, result, dataset, code/parameter change, hypothesis, literature evidence or plan amendment. Each mutation proposal records its exact source branch, target object/version, base revision, proposed change/diff, provenance, validation, author/agent, expected consequences and accept/reject decision. **Acceptance records the scientific change. Any computation required to materialize or validate that change is separately admitted under the applicable execution and resource permissions.** Accepting a note or plan amendment launches no computation. A request for a canonical rerun is not standing execution permission. Presentation-only edits continue to launch zero numerical/model stages.

An LLM may propose a method, implementation, validation cases or promotion; it cannot convert that proposal into approved scientific policy. Execution must remain subject to controller-enforced admission, resource limits, provenance and an explicitly supported isolation boundary; existing worker supervision is not proof of arbitrary-code security containment. Researcher review determines scientific acceptance and scoped promotion. A MethodVersion contract does not authorize implementing or running the audit's CellBender, DoubletFinder or 4-MAD examples.

## Metadata evolution and exact references

Atomic JSON with revisions remains the bounded local storage choice. Before persisted annotations, branches, proposals, canonical pointers, multi-project permissions and other related mutable records accumulate, introduce a transactional metadata store such as SQLite with explicit migration and crash-recovery guarantees. Keep immutable scientific evidence in its existing stores, mutable identities/relationships/projections in the metadata layer, and secrets/runtime state outside both UI restoration and scientific records. Store controller references and reconciled projections rather than a second authoritative execution state machine.

Every supported schema migration must be explicit, validated and recoverable, preserve stable IDs/version references and sealed evidence, and retain stale-writer protection. Unsupported schema versions must not be guessed or silently reset. Deletion/unavailability requires a tombstone or equivalent retained identity/status: IDs are not reused, historical relationships remain interpretable under current access rules, and missing materializations are distinguished from missing logical objects. Exact-version deep links resolve that version or report unavailable/changed; they never silently follow a latest/canonical pointer. Migration, recovery and tombstones do not invent scientific evidence or grants.

## Staged acceptance

The stages below are requirements, not completed backend capabilities. Preserve M2a evidence and the unresolved T14 result throughout; organization work does not start M2b or change scientific gates.

1. **Local organization and persistence.** Verify same path/new bytes → distinct verified content; different paths/same bytes → shared content identity with both registrations retained; uninspected inputs remain unverified. Search reads retained metadata only. Input inspection remains activity; presentation edits launch zero numerical/model stages. Restore exact route/version/filter/zoom/draft and explicit missing-artifact state without kernel or authorization restoration. Test stale writers, invalid/unsupported metadata, interrupted writes, validated backup and explicit recovery, compatible migration and retained invalid evidence. A failed durability step must not be reported as a completed durable save. Verify exact provenance identities and preserve unknown liveness. The [audit checkpoint](../reports/rna-agent-readiness/2026-09-27-organization-audit.iro5gaqt/README.md) records label, migration, recovery and preservation evidence with its verification limits.
2. **Scientific object foundations.** Implement Study/Dataset/Analysis IDs and versions, intentional Run versus ExecutionAttempt, separate Result/Artifact relationships and exact-version links. Test rename/move invariance, multi-file manifest changes, scientific code/parameter versioning, separate reruns versus scheduler retries, and cosmetic edits without new scientific AnalysisVersions. Migration/tombstone checks must preserve sealed evidence and missing-version disclosures. Decide remote locators from the deployment contract.
3. **Method foundations.** Implement experimental MethodVersions with reusable I/O contracts, implementation provenance, scoped trust and ValidationRecords before multi-project sophistication. Under separately admitted bounded fixtures, demonstrate proposal → isolated execution → recorded validation → local scientific acceptance → revised AnalysisVersion → attributable reuse and later explicit promotion. Retain failed validation and the old approved plan. No named method or statistical threshold is automatically approved by this scenario.
4. **Anchored discussion.** After establishing transactional metadata, persist annotations/branches and immutable context snapshots. Test exact anchor restoration, visible stale bases, missing artifacts without retargeting, permission revocation after branch creation, current access intersection and absence of secret/kernel/job-control inheritance.
5. **Governed changes.** Implement locked plans/amendments, typed proposals, rejection history and scoped canonical pointers. Test stale target rejection/explicit rebasing, exact diffs and consequences, immutable old versions, actor/time/basis, replacement within one canonical scope without deletion or changes to other scopes, and acceptance with no computation until separately admitted. Cosmetic edits need no methodological amendment and launch no numerical stage.
6. **Multi-project/remote continuation.** Establish actual project permissions, cross-project activity and ownership-aware remote reconciliation before advertising them. Test revoked access and unknown liveness. A local browser over remote data/compute remains a product requirement, not a capability of this loopback service.

Optional later capabilities: collections/tags/custom fields, provenance graph browsing, templates, multiple reviewers, semantic search, shared datasets, schedules, coediting and RO-Crate/DOI export. The object/provenance contracts do not require a graph-first interface or immediate standards export, and do not authorize integrations or external communications.
